# Go 리팩토링

사용자가 지정한 패키지나 변경분에서 시작한다. 리뷰를 요청하면 근거와 제안을 전달하고, 리팩토링을 요청하면 변경을 구현하고 검증한다. 관점을 지정하면 그 관점에 집중한다. 전체 요청이면 아래 일곱 질문을 같은 코드 경로에 대입한다. 한 변경이 여러 질문에 답할 수 있고, 그대로 두는 편이 나은 코드도 있다.

## 변경과 검증

1. 실제 호출자에서 시작해 대상 경로를 따라간다. 성공 결과와 실패 결과 중 이번 변경으로 달라질 수 있는 계약을 적고, 가장 가까운 기존 테스트나 실행 예제로 기준값을 얻는다.
2. 후보마다 어느 호출자나 유지보수 작업이 쉬워지는지 설명한다. 관점끼리 다른 방향을 제안하면 관찰한 계약을 보존하면서 문제를 해결하는 가장 작은 변경을 택한다. 동작 차이를 발견하면 별도 수정 후보로 보고한다.
3. 같은 입력을 원래 진입점에 다시 넣어 비교한다. 순서, 중복, 오류 판별, 취소, 출력 바이트 중 호출자가 의존하는 항목을 고른다. 동시성을 건드렸다면 종료 경로와 경쟁 검사를, 직렬화를 건드렸다면 실제 응답과 빈 결과를 확인한다.
4. 변경한 Go 파일에 `gofmt`를 적용하고 대상 패키지 테스트를 실행한다. 영향 범위에 따라 저장소의 검증 명령, `go vet`, `go test -race`를 사용한다. 결과에는 어떤 책임이 어디로 이동했는지와 어떤 입력으로 동작 보존을 확인했는지 적는다. 실행하지 못한 검증은 구분한다.

예를 들어 목록 API와 다운로드 API가 같은 공개 규칙을 사용한다면, 두 경로가 합의해야 하는 판정만 공유한다. 목록의 정렬·중복 처리와 다운로드의 오류 응답은 각 호출자가 소유한다. 변경 전후에 같은 항목을 두 API에 요청하면 판정의 일치와 각 경로의 응답 계약을 따로 검증할 수 있다.
